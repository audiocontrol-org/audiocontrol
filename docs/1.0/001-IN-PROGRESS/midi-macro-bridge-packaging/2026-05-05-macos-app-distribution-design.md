# macOS `.app` + `.dmg` distribution

## Problem

The v0.1.0 release ships per-platform tarballs and a Homebrew tap. Both require Terminal interaction for end users:

- Homebrew requires `brew tap` + `brew install` from the shell.
- The tarball requires `tar`, `xattr -d com.apple.quarantine`, and either `install.sh` or manual file placement.

The user wants a Mac-native install path: download → drag to Applications → double-click. No Terminal. The control interface is the existing embedded web UI, but framed as an app window (not a browser tab) so it feels like a real Mac application.

## Solution overview

Ship a signed and notarized `MidiMacroBridge.app` inside a signed and notarized `.dmg` alongside the existing tarballs. Reuse the macOS code-signing and notarization infrastructure that already lives in the sibling `midi-server` project.

The Rust binary stays the same. A new `--gui` flag (auto-detected when the binary launches from inside a `.app` bundle) opens a native AppKit window via the `wry` Rust crate. The window hosts a `WKWebView` pointed at `http://127.0.0.1:8765` — the bridge's existing web UI renders inside it unchanged.

When the user closes the window, the bridge runs the same graceful shutdown path that the existing **HALT** button triggers (`Cmd::Halt` → MIDI loop drain → `process::exit(2)`).

## Architecture

### Bundle layout

```
MidiMacroBridge.app/
├── Contents/
│   ├── Info.plist                   # bundle ID, version, executable name, icon ref
│   ├── MacOS/
│   │   └── midi-macro-bridge        # the existing Rust binary, signed
│   ├── Resources/
│   │   └── AppIcon.icns             # placeholder for v0.2.0; real icon ships later
│   ├── _CodeSignature/              # generated by `codesign`
│   └── PkgInfo                      # required Apple plist marker
```

### Launch flow

1. User double-clicks `MidiMacroBridge.app`. macOS launchd executes `Contents/MacOS/midi-macro-bridge` with no arguments.
2. Binary detects bundle context: `std::env::current_exe()` returns a path containing `.app/Contents/MacOS/` → binary internally enables GUI mode (no need for the bundle to inject `--gui` via wrapper script).
3. Bridge runs its existing startup: parse config via the `paths::resolve_config_path` chain (delivered in Phase 1), bind web server on `127.0.0.1:8765`, register MCU virtual endpoint, write `url.txt` to the namespaced state dir.
4. Under GUI mode: instead of calling the existing `open <url>` to launch the user's default browser, the binary creates a `tao` event loop on the main thread and attaches a `wry::WebView` window pointed at `http://127.0.0.1:8765`.
5. User sees a native AppKit window showing the existing HTMX UI: status panel, config form, event stream, HALT button. Same controls as today's browser-based UI; only the frame changes.
6. User closes the window (red X / Cmd-W) → wry's window-close event handler invokes the same `Cmd::Halt` path as the HALT button → bridge exits cleanly.

### Headless / service modes unchanged

- `brew services start midi-macro-bridge` and the launchd plist (Phase 2) launch the binary without the bundle context. Bundle detection returns false, GUI mode stays off, existing browser-auto-open behavior fires (or doesn't, depending on `web.auto_open_browser`).
- `--gui` flag remains available for explicit testing without a bundle.
- `--no-gui` flag forces GUI off even when launched from a bundle (useful for debugging the headless path from an installed `.app`).

## Components

### `gui.rs` module (new)

~30 lines of Rust, gated by `cfg(target_os = "macos")` initially.

```rust
pub fn run_window(url: &str, halt: HaltHandle) -> Result<()> {
    // Build tao event loop on main thread.
    // Create one window, attach wry WebView pointed at `url`.
    // On window-close event: halt.send().
    // Drive event loop until halt fires or user closes.
}
```

Public surface: `run_window(url: &str, halt: HaltHandle) -> Result<()>`. The `HaltHandle` is the existing channel that the HALT button posts to; `gui.rs` reuses it instead of inventing a new shutdown path.

### `main.rs` change

After web server binds and `url` is known:

```rust
if force_gui_mode() {  // bundle detection or --gui flag
    gui::run_window(&url, halt_handle.clone())?;
    // run_window blocks until window closes; bridge exits afterward.
} else if config.web.auto_open_browser && !no_open {
    open_browser(&url);  // existing path
}
```

The wry event loop must own the main thread on macOS. The MIDI thread, web server thread, and SSE broadcaster move off the main thread (they already do — only the event loop is new).

## Signing pipeline

```
1. cargo build --release --target aarch64-apple-darwin   # already done by package-macos
2. mkdir -p MidiMacroBridge.app/Contents/{MacOS,Resources}
3. cp target/aarch64-apple-darwin/release/midi-macro-bridge MidiMacroBridge.app/Contents/MacOS/
4. write Info.plist + PkgInfo from templates (version substitution)
5. cp packaging/macos/AppIcon.icns MidiMacroBridge.app/Contents/Resources/
6. codesign --options runtime --entitlements entitlements.plist \
     --sign "$DEVELOPER_ID_APP" MidiMacroBridge.app/Contents/MacOS/midi-macro-bridge
7. codesign --options runtime --entitlements entitlements.plist \
     --sign "$DEVELOPER_ID_APP" MidiMacroBridge.app
8. codesign --verify --deep --strict MidiMacroBridge.app
9. mkdir dmg-staging && cp -R MidiMacroBridge.app dmg-staging/ \
     && ln -s /Applications dmg-staging/Applications
10. hdiutil create -volname "MIDI Macro Bridge" \
       -srcfolder dmg-staging/ \
       -ov -format UDZO \
       MidiMacroBridge-v0.2.0.dmg
11. codesign --sign "$DEVELOPER_ID_APP" MidiMacroBridge-v0.2.0.dmg
12. xcrun notarytool submit --apple-id "$APPLE_ID" \
       --password "$APPLE_APP_SPECIFIC_PASSWORD" --team-id "$APPLE_TEAM_ID" \
       --wait MidiMacroBridge-v0.2.0.dmg
13. xcrun stapler staple MidiMacroBridge-v0.2.0.dmg
14. spctl --assess --type install -vv MidiMacroBridge-v0.2.0.dmg
```

Credentials sourced from the existing midi-server `release-secrets.sh`. No new credential infrastructure.

### Entitlements

Minimal; `packaging/macos/entitlements.plist`:

```xml
<key>com.apple.security.network.server</key>     <true/>
<key>com.apple.security.network.client</key>     <true/>
```

No `com.apple.security.cs.allow-jit` (no JIT), no `com.apple.security.cs.disable-library-validation` (no plugins), no app sandbox (sandboxing prohibits CoreMIDI virtual endpoint creation, which is core to this app's purpose).

## Build flow integration

New Makefile targets:

| Target | Description |
|---|---|
| `make package-app VERSION=v0.2.0` | Assemble + sign `.app` only (fast iteration during dev) |
| `make package-dmg VERSION=v0.2.0` | Full pipeline: assemble + sign `.app`, build `.dmg`, sign + notarize + staple |
| `make package-all VERSION=v0.2.0` | Existing target; will be extended to include `package-dmg` |

`release.sh` extended: after `package-all`, the `gh release create` invocation gains the `.dmg` and its `.sha256` as additional assets. `SHA256SUMS` aggregate gains the `.dmg` line.

## Acceptance criteria

1. `make package-app VERSION=v0.0.2-test` produces a signed `MidiMacroBridge.app`. `codesign --verify --deep --strict` passes.
2. Double-click the `.app` from Finder → a native AppKit window opens within ~2s showing the bridge's existing HTMX UI. The HALT button quits the app cleanly. Closing the window (red X / Cmd-W) also quits cleanly.
3. `make package-dmg VERSION=v0.0.2-test` produces a signed and notarized `.dmg`. `spctl --assess --type install` passes.
4. Mounting the `.dmg`, dragging `MidiMacroBridge.app` to Applications, and double-clicking from `/Applications` reproduces the same launch flow as #2 — confirms `paths.rs` resolution works for an installed `.app`.
5. Brew install (`brew install audiocontrol-org/audiocontrol/midi-macro-bridge`) and tarball install (Phase 2 + 3) continue to work unchanged. The new GUI code path is gated by bundle detection or `--gui` flag and does not affect the headless service modes.
6. `make release VERSION=v0.2.0` includes the `.dmg` in the GitHub Release alongside the existing tarballs.
7. Phase 6 regression check (no `MIDI channel disconnected` within 2.5s of default-config startup) still passes for the GUI-launched binary.

## Out of scope for v0.2.0

- Status bar icon / menubar item (defer to v0.3 — adds `tray-icon` crate)
- Single-instance lock (defer to v0.3)
- macOS Login Items registration (user adds manually if wanted)
- Auto-updater (Sparkle or similar) — user re-downloads `.dmg`
- Linux / Windows GUI — wry supports both, but those install paths are covered by tarball + brew today
- Custom DMG background image / window layout — plain `hdiutil create` is enough; pretty DMG via `create-dmg` is polish for later
- Universal binary (Intel + arm64) — arm64 only for v0.2; Intel is in the project's broader Out of Scope list
- Real icon — placeholder for v0.2; commission an icon when there's user demand
- Bundle the binary inside the brew formula (so brew users get a `.app` too) — defer; brew is the headless service path

## Open questions (resolved or accepted defaults — not blockers)

- **Where do midi-server signing scripts live in CI/another machine?** Default assumption: same path as orion-m4. Add `AUDIOCONTROL_SIGNING_INFRA_DIR` env var so the path is overridable. Document in implementation plan.
- **What happens if the user double-clicks the `.app` while a bridge instance is already running?** Today's CoreMIDI UniqueID collision behavior triggers cleanly; the new instance fails to register the virtual endpoint and exits. The wry window shows a connection-refused error on first paint. Acceptable for v0.2; v0.3 adds proper single-instance lock with focus-existing-window.
- **Quit menu?** macOS `Cmd-Q` doesn't get a menu by default with wry. The standard tao window handles `Cmd-W` (close window) and that triggers our halt path. `Cmd-Q` is a nice-to-have; defer to v0.3 with proper menubar.

## Verification trade-offs (deferred from this phase)

- The notarized `.dmg` smoke test requires a network round-trip to Apple's notary service (~2-5 min wait). The `make package-app` target skips notarization for fast iteration; full notarization runs only via `make package-dmg` and `make release`.
- Gatekeeper assessment (`spctl --assess`) requires the binary be on the host where `make release` runs. CI assessment is out of scope (no CI for this project per Phase 3 reshape).
