▸ Setup guide · prepare your device for SysEx control 7 steps · 2 min video

Before the editor can read or write to your {{deviceName}}, the device itself needs to be put into a mode where it accepts SysEx. The steps differ slightly between the S-330 and S-550, but the procedure is the same shape.

Tutorial · {{videoDurationLabel}}

Step by step:

  1. 1 Power on the {{deviceName}} and wait for the home screen.
  2. 2 Press MIDI on the front panel.
  3. 3 Confirm EXC ON is set (Exclusive accepted).
  4. 4 Note the Device ID shown on the screen — enter the same value in the editor's Device ID field (1–17, defaults to 1).
  5. 5 Connect the {{deviceName}}'s MIDI OUT to your interface's MIDI IN.
  6. 6 Connect your interface's MIDI OUT to the {{deviceName}}'s MIDI IN.
  7. 7 Press Connect in the editor. The status LED above will turn green and the connection state will read Connected.
▸ Troubleshooting · the editor can't reach the device common fixes
  • Confirm the MIDI interface appears in BOTH the Input and Output dropdowns. For most operators it should be the same interface in both.
  • If your browser prompted for Web MIDI access on first load, click Allow. Without that permission the editor can read MIDI events but cannot write changes to {{deviceName}}.
  • On the device itself, the MIDI menu's EXC setting must be ON for the editor to read or write patches and tones. (Setup Guide → step 3.)
  • The {{deviceName}} displays IDs 1–17 on the front panel but the underlying MIDI protocol value is 0–16. The form here uses the front-panel value, so match what your device shows.
  • Some MIDI interfaces require their own utility to be running. Make sure the interface is recognized by macOS / your OS before reloading the editor.
  • If a previous connection left the device in an odd state, power-cycle the {{deviceName}} and reload the page.

Direction A · VFD status display

The device's VFD display is the visual anchor. The connection state is the primary content: glowing LED + uppercase status line + parameter readout. The form below renders as a sequenced checklist (01 / 02 / 03) so the operator has a clear procedural sense of "what do I need to fill in".

Runtime-templated values:

  • {{deviceName}} — both editors share this screen; binds to useDeviceConfig().deviceName (e.g. Roland S-330, Roland S-550). Appears in the eyebrow, the VFD detail row, and the setup-guide / troubleshooting copy. No string is hardcoded to a specific device.
  • {{videoDurationLabel}} — caption under the tutorial play target; rendered when video metadata is loaded.

Action button label flips with state:

  • Disconnected → Connect
  • Connecting → Connecting… (disabled)
  • Connected → Disconnect
  • Error → Retry

Learn-more disclosures (collapsed by default):

  • Setup guide — first-run procedural walkthrough with an embedded 2-minute tutorial video and a 7-step checklist for putting the device into SysEx-accepting mode. Sits above troubleshooting because operators are more likely to need it on first connect.
  • Troubleshooting — common fixes when the editor can't reach the device. Same content as today's static help block, restyled and demoted from peer-of-the-form to hidden-by-default.

Strengths: direct visual mapping to the device. State of the connection is unmissable. The procedural checklist tells the operator "you've set everything; click CONNECT". Learn-more material is one click away but never competes with the primary action.

Trade-offs: the VFD chrome is heavier than the rest of the editor and may compete for attention with the CRT on other pages. Animation / glow accents have a small maintenance cost (color tokens to keep in sync if the palette evolves).

Three transport variants, one configuration panel: the form between the VFD and the CONNECT button swaps content based on the active transport.

  • Web MIDI API (default) — MIDI Input + MIDI Output dropdowns + Device ID.
  • HTTP MIDI Server — Server URL (with a Test mini-button) + live reachability readout (green LED + latency) + Device ID. Used for the SCSI-bridge / Pi rig.
  • Mock — Scenario picker (tones-bank-0, patches-bank-0, full-snapshot, empty) + Device ID + a small "for testing only" note. Drives the fixture-based simulated MIDI harness.

The checklist chrome (numbered rows, status dots, label-over-control) is identical across all three so the operator's perception of "where things go" doesn't shift when they switch transports — only the per-row content does.

Transport selector position: the .ac-toggle segmented control (WEB MIDI · HTTP · MOCK) lives below the CONNECT button — it's the least-important control on the page (set-and-forget for 99% of operators) and shouldn't compete for attention with the configuration above. The toggle still updates the VFD readout + the disclosure summary + the visible config panel synchronously when switched. The inline change link in the VFD Transport row scrolls to + opens the disclosure as an alternative trigger.

Choice-selector language: the toggle uses the established .ac-toggle chrome — same byte-for-byte family as BANK A|B, LOOP MODE FWD|ALT|ONE|REV, and OUTPUT MIX|1-8 on the Tones editor.
